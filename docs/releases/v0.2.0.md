# basis-gateway v0.2.0 Release Notes

**Release date:** 2026-08-03
**Status:** Published release

See [`docs/release-checklist.md`](https://github.com/basis-foundation/basis-gateway/blob/v0.2.0/docs/release-checklist.md)
for the checklist used to prepare this release.

---

## Overview

`basis-gateway` v0.2.0 adds a feature-gated, additive **operation-aware** evaluation path
(`POST /v1/evaluate/operation-aware`) alongside the existing v0.1 evaluation path
(`POST /v1/evaluate`), which remains supported, unchanged, and byte-for-byte unaffected by this
release.

The operation-aware path delegates to `basis-core`'s public `OperationAwareEnforcementPoint`. It
adds explicit, configuration-driven trusted operation-producer classification; action and resource
composition shared with the v0.1 path; field-level provenance so producer-supplied operational
context can never be silently accepted from an untrusted caller; a startup semantic preflight that
closes the "structurally loaded but semantically broken bundle" gap; exact HTTP classification of
every kernel `evaluation_status`/`outcome`/`failure_reason` combination; and gateway-and-kernel
audit evidence recorded as linked sibling artifacts in the same durable record.

---

## What is new

- **Feature-gated operation-aware endpoint** — `POST /v1/evaluate/operation-aware`, registered
  only when `OPERATION_AWARE_ENABLED=true`. Uses the same Bearer-token authentication as
  `/v1/evaluate` (`AUTH_MODE=oidc` or `AUTH_MODE=basis_local_token`, never both, never inferred).
- **Operation-producer trust** — an explicit, configuration-driven, exact-match, case-sensitive
  subject-ID allowlist (`OPERATION_PRODUCER_SUBJECT_IDS`), empty by default. No caller is a
  trusted producer without explicit configuration; roles and token issuer never imply producer
  trust.
- **Request ownership / provenance gating** — an authenticated caller not classified as a trusted
  operation producer that supplies any producer-only field (`operation_intent`, `location`,
  `device`, `protocol_context`, `safety_context`, `environment_context`, `risk_context`,
  `identity_evidence_reference`, `adapter_evidence_reference`) is rejected (`400`) before the
  kernel is ever invoked.
- **Action and resource composition** — reuses the same adapter-normalized (bare verb +
  `resource_type`) composition boundary already used by `/v1/evaluate`, unchanged.
- **Semantic preflight** — a startup-time check against a synthetic, reserved request through the
  same real public enforcement path, so a bundle that structurally loads but is semantically
  invalid (e.g. duplicate rule IDs, unsupported condition operators) is caught before the service
  becomes ready, not on the first real request.
- **Kernel integration through the public `basis-core` API only** — `OperationAwareEnforcementPoint.for_bundle()`;
  no import of `basis_core.evaluation.*` or any other internal symbol anywhere in this repository.
- **Exact result classification** — a single, exhaustively tested function maps every kernel
  `evaluation_status`/`outcome`/`failure_reason` combination to an HTTP status
  (`200`/`400`/`403`/`500`/`503`); `NOT_APPLICABLE` is never rewritten to `"deny"` in the response
  body, even though both currently map to HTTP `403`.
- **Audit evidence** — a contract-shaped `GatewayAuditEvent` recorded beside (never nested inside)
  the kernel's complete, unmodified `AuditEvidence` in the same durable record, linked by
  `gateway_audit_event.audit_evidence_id == audit_evidence.evidence_id`. The audit writer and its
  failure-escalation/fail-closed behavior are shared, unchanged, across both endpoints.
- **Readiness** — four additional, stage-specific readiness components
  (`operation_aware_mode_enabled`, `operation_aware_bundle_loaded`,
  `operation_aware_evaluator_initialized`, `operation_aware_policy_semantically_valid`),
  registered only when the feature is enabled.
- **Conformance** — a canonical conformance suite covering the primary outcome scenarios, and a
  broader adversarial/mutation-based conformance suite exercising the real gateway-to-kernel path.
- **Offline demonstration** — a reproducible, bounded, offline walkthrough of the real
  gateway-to-kernel path (`demo/operation-aware/run_demo.py`) covering all six governed scenarios.

See [`docs/operation-aware-endpoint.md`](https://github.com/basis-foundation/basis-gateway/blob/v0.2.0/docs/operation-aware-endpoint.md) for the full
request/response reference and [`docs/audit-model.md`](https://github.com/basis-foundation/basis-gateway/blob/v0.2.0/docs/audit-model.md) for the audit model.

## Compatibility

- `POST /v1/evaluate` **remains supported and unchanged**. No shared route, request/response
  model, or authorization behavior is affected by the operation-aware addition.
- Operation-aware mode is **disabled by default** (`OPERATION_AWARE_ENABLED=false`) and requires
  explicit configuration to enable. A deployment that does not set this flag observes zero
  behavior change from v0.1.0.
- Both evaluation paths may be enabled and served simultaneously on the same running instance,
  sharing the same authentication configuration and the same `GatewayAuditWriter` instance.
- Dependency requirement: `basis-core>=0.2.1,<0.3.0` (verified against `pyproject.toml` — the
  floor matches the version that introduced the public `OperationAwareEnforcementPoint.for_bundle()`
  factory this integration depends on; the upper bound excludes the next breaking increment).

## Configuration

The operation-aware path is configured with (exact variable names):

- `OPERATION_AWARE_ENABLED` — enables the route and the four operation-aware readiness
  components. Default: `false`.
- `OPERATION_AWARE_POLICY_BUNDLE_PATH` — path to the JSON operation-aware `PolicyBundle` file.
  Required when `OPERATION_AWARE_ENABLED=true`.
- `OPERATION_PRODUCER_SUBJECT_IDS` — comma-separated, exact-match, case-sensitive allowlist of
  subject IDs trusted to assert operation-producer-only context. Default: empty (no caller is
  trusted).

Both evaluation paths share the same authentication configuration (`AUTH_MODE` and its associated
variables) and the same audit configuration (`AUDIT_FAILURE_THRESHOLD`, `AUDIT_FAIL_CLOSED`). See
[`docs/configuration.md`](https://github.com/basis-foundation/basis-gateway/blob/v0.2.0/docs/configuration.md) for the complete environment-variable reference —
not duplicated here.

## Security model

- **Exact, case-sensitive producer allowlist.** `OPERATION_PRODUCER_SUBJECT_IDS` matches subject
  IDs exactly; no wildcard, prefix, or case-insensitive matching exists.
- **No role-based producer trust.** Roles and token issuer never imply operation-producer status —
  only exact allowlist membership does.
- **No caller-controlled identity.** Subject identity is derived exclusively from the verified
  Bearer token, identical to the v0.1 path.
- **No caller-controlled gateway provenance.** An untrusted caller supplying any producer-only
  field is rejected (`400`) before the kernel is invoked; provenance evidence cannot be forged.
- **Fail-closed enforcement.** Every non-`ALLOW` kernel result blocks; the HTTP classification
  function has no permissive default or fallthrough.
- **Kernel outcomes are preserved, not reinterpreted.** `evaluation_status`, `outcome`,
  `failure_reason`, and `disposition` are returned exactly as `basis-core` produces them.
  `NOT_APPLICABLE` is never collapsed into `"deny"` in the response body.
- **No fabricated kernel evidence.** When the kernel is never invoked (e.g. producer-context
  rejection), no `AuditEvidence` or `GatewayAuditEvent` claiming a kernel evaluation is written.
- **No physical-execution claim.** The gateway proves an authorization decision, an enforcement
  disposition, and an HTTP result — it does not prove that a physical device executed the
  requested operation.

## Demonstration

```bash
python demo/operation-aware/run_demo.py
```

A reproducible, bounded, offline demonstration of the real gateway-to-kernel path — no network
access, live identity provider, Docker, or external secrets required. Exercises all six governed
scenarios against the real `POST /v1/evaluate/operation-aware` route via
`fastapi.testclient.TestClient`, with real authentication (an ephemeral, in-memory-signed
BASIS-local token) and the real `basis-core` kernel:

- **allow**
- **explicit deny**
- **default deny**
- **not_applicable**
- **untrusted producer** (producer-context rejected before the kernel is invoked)
- **semantic startup failure** (structurally valid, semantically invalid bundle — duplicate
  `rule_id`)

See [`demo/operation-aware/README.md`](https://github.com/basis-foundation/basis-gateway/blob/v0.2.0/demo/operation-aware/README.md) for the full
walkthrough and output format.

## Known limitations

- No policy hot reload — both the v0.1 role-table policy and the operation-aware `PolicyBundle`
  are loaded once at startup; changes require a restart.
- No remote policy distribution — policy and bundle files are loaded from a local filesystem path.
- No durable, database-backed audit store — audit events are written through `LogAuditWriter`
  (process log) only.
- No audit query API.
- No cryptographic audit signing.
- No tamper-evident audit chain.
- No adapter execution confirmation — the gateway proves an authorization decision, an enforcement
  disposition, and an HTTP result; it does not prove that a physical device executed the
  operation.
- No device-state verification.
- No background policy revalidation — the operation-aware startup semantic preflight runs once,
  at startup.
- No built-in multi-tenancy.
- No hosted-service control plane.
- Operation-aware `basis-console` UI integration (Training mode, Operator mode) is not implemented
  in this repository — planned as follow-on work in the `basis-console` repository.
- Three governed failure reasons (`invalid_request`, `unsupported_schema_version`,
  `internal_evaluation_error`) are documented and exhaustively covered at the HTTP-classification
  level, but are not reachable through the real gateway-to-kernel path with a structurally valid
  bundle in this repository's own test suite.

This is a pre-production proof of concept, consistent with the v0.1.0 release. It is not
production-certified, does not confirm device execution, does not provide durable audit
persistence, is not a hosted service, and does not include completed `basis-console` integration,
protocol-adapter execution, tamper-evident audit storage, multi-tenancy, or high availability.

## Upgrade guidance

This is not a breaking migration for existing v0.1 users.

- Existing configuration continues to work unchanged. No environment variable used by v0.1.0 has
  changed meaning, default, or validation behavior.
- Operation-aware mode remains **disabled** unless `OPERATION_AWARE_ENABLED=true` is explicitly
  set.
- No migration of `/v1/evaluate` callers is required — the endpoint, request/response schema, and
  authorization behavior are unchanged.
- Consumers opting into operation-aware mode must provide a compatible `PolicyBundle` file
  (`OPERATION_AWARE_POLICY_BUNDLE_PATH`) and a `basis-core` installation satisfying
  `>=0.2.1,<0.3.0`.
- `/ready` gains four additional components only when `OPERATION_AWARE_ENABLED=true`; deployments
  that leave the flag unset see no change to their existing readiness contract.
